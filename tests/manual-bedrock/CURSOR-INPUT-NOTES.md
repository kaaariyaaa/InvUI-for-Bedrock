# カーソル取得によるクリック検出の調査・実機試験メモ（統合しない）

> [!WARNING]
> `ef2e079`（worktree `parallel-ui-transport`）の「カーソル取得 + `virtualContainerItemChange` の復元でクリックを判定する」試作は、**複製危険があるため main へ統合しません**。この文書はその判断理由と、実機で観察する項目を残すための調査記録です。
>
> **ここに書いた経路を製品実装・有効化手順として案内しないでください。** 実装コードは main にありません。実機で試す場合も使い捨てワールドだけで行い、表示アイテムの保護や設計 10.8 の合格根拠にしないでください。

## 2. 何を試したか（要約）

- JSON UI から slot 番号を script へ自動で渡す binding は、公式 sample では確認できていません（[API-NOTES.md](API-NOTES.md)、[README.md](README.md) のクリック通知節と同じ結論）。
- 試作は `virtualContainerItemChange` が持つ `slot` を slot の取得元にし、プレイヤーの `cursor_inventory.item` が変更前の stack と一致するかで「通常クリック」と「ドロップ・Shift クリック」を区別しようとしました。
- 一致した場合、試作はスロットへ変更前の stack を書き戻し、カーソルを clear してから、button slot だけをクリックとして `Window.handleClick()` へ流します。
- chat・session-id・sequence・`button.send`・`button.drop_one` は使いません。オプトインで、display slot は復元のみです。

## 3. 統合しない理由

### 3.1 after イベントでの復元は原子的でない

`virtualContainerItemChange` は変更後の通知です。復元（`setItem`）と `clear()` の間に例外・クラッシュ・再読み込みが起きると、同じスタックがスロットとカーソルの両方に残り得ます。逆に clear に失敗してスロットを空へ戻す経路も、その後のゲーム側のカーソル処理まで保証できません。**復元が成功したことと、アイテムが 1 個だけであることは別です。** after イベントである以上、この経路を保護として扱えません。

### 3.2 同一指紋ではスタックを区別できない

比較は `typeId` / `amount` / `nameTag` / lore / tags / lock mode / keepOnDeath の fingerprint で、どのスタックかという同一性はありません（Bedrock に `ItemStack.equals()` がないため）。

- **同一指紋のスタックをカーソルに持ったまま Shift クリック**: Shift クリックで slot からインベントリへ移った後も、カーソルには元から持っていた同一指紋のスタックが残ります。試作はこれを「クリックでカーソルへ移った分」と誤認し、slot を復元してカーソルを clear します。結果として、**インベントリへ移った分と復元した slot 分が併存し、カーソルに持っていた元のスタックは消える**ため、スロット内容の複製とカーソル側の消失が起こり得ます。
- **同一指紋のスタックをカーソルに持ったまま通常クリック（持ち出し）**: 同じく復元対象とカーソル上の既存スタックを取り違え、clear が既存スタックを消す一方で slot が復元されます。個数が合わなくなり、その後の再描画でさらに増減し得ます。
- 列挙していない component の差も区別できません。

### 3.3 イベント順序が未文書化

`virtualContainerItemChange` の時点で `cursor_inventory.item` が更新済みかは公式に保証されていません。順序が逆ならクリックは検出されず fail closed になりますが、順序が環境依存なら判定結果も環境依存になります。

### 3.4 タッチでは成立しない

`PlayerCursorInventoryComponent` は「touch controls では使われない」と明記されています。**タッチ入力ではカーソルが存在しないため、この経路ではクリックを検出できません。** コントローラーの gamepad cursor が同じ component を使うかも未確認です。設計 10.8 の全入力方式の合格には足りません。

### 3.5 クリック検出であって保護ではない

入力抑制も JSON UI も使わないため、Shift クリック・ドラッグ・ドロップはゲーム側で処理され続けます。表示アイテムは一瞬カーソルへ移ります。ドロップや Shift クリックを danger として close するだけであり、設計 10.1 の「取り出せない」も 10.8 の合格も満たしません。API も beta / rc です。

## 4. 実機で観察する項目（実施しても合格根拠にしない）

以下は**観察項目**であり、復元経路を製品として有効化する手順ではありません。実施環境は [README.md](README.md) の「3. 実施環境の記録」に合わせ、ゲーム版・`@minecraft/server` 版・プラットフォーム・入力方式・画面サイズを残してください。**これらの ID を CHECKLIST の `CLICK-*` / `PROT-*` に流用せず、実施済み・合格として扱わないでください。**

| ID | 操作 | 観察すること |
|---|---|---|
| CUR-01 | PC・空のカーソルで表示/ボタン slot を通常クリック | itemChange が 1 回か。`beforeItemStack` / `itemStack` / cursor の更新順。クリックが 1 回だけ検出されるか |
| CUR-02 | PC・カーソルに slot と同一指紋のスタックを持った状態で Shift クリック | スロット・インベントリ・カーソルの個数。複製または消失が起きるか |
| CUR-03 | PC・カーソルに同一指紋のスタックを持った状態で通常クリック（持ち出し） | 同上。clear 後に既存スタックが消えないか |
| CUR-04 | PC でドロップ、ドラッグ、ダブルクリック相当 | クリックと誤判定されないか。画面が danger 側で閉じるか |
| CUR-05 | カーソルにアイテムを持ったまま画面を閉じる・死亡する・次元移動する | カーソル上のアイテムが消失しないか。復元や clear と競合しないか |
| CUR-06 | タッチでタップ、長押し、ドラッグ | `cursor_inventory` が存在しない、または更新されないこと。クリックが検出されないこと |
| CUR-07 | コントローラーでカーソルを合わせて決定、ドラッグ相当 | gamepad cursor が同じ component を使うか。判定が PC と同じか |
| CUR-08 | 画面を閉じた後・ページ変更後に遅れて itemChange が届く状況 | 古い変更がクリックとして実行されないか |

記録には、操作前後のスロット・インベントリ・カーソルの個数、`beforeItemStack` / `itemStack` の有無、itemChange の発火回数、cursor の更新タイミングを含めます。**複製・消失が 1 件でも観測したら中止**し、それ以上この経路を試さないでください。

## 5. 現時点の結論

- `ef2e079` のカーソル復元経路は統合しない。同一指紋の Shift クリック・持ち出しの誤判定と、after イベント復元の非原子性により、複製・消失を排除できない。
- タッチではカーソルが使われないため、この経路だけでは全入力方式を満たせない。
- クリック通知は引き続き未確定であり、`CLICK-*` は未実施のままとする。表示アイテムの保護も未実装のままとし、`PROT-*` の合格根拠にしない。
- 再検討するのは、イベント順序とカーソル更新が公式に保証され、スタックの同一性を判定でき、復元が原子的に行える API が示された場合に限る。それまでは復元を前提にした設計・実装を案内しない。
