# Bedrock 実機テスト手順（フェーズ0）

このディレクトリは、InvUI for Bedrock の**実機未検証機能**を安全に検証するための手順と合否基準をまとめたものです。設計書のフェーズ0（技術検証）に対応します。

> [!WARNING]
> **コアは実装済みですが、実機で画面を開く経路と配布用 JSON UI はまだ用意されていません。**
>
> - コア（レイアウト計算、アイテム、`VirtualInventory`、状態管理、`Window` のライフサイクル）は `src/` に実装され、Node.js の自動テストで確認されています。実機動作の保証ではありません。
> - `Window.open()` は既定で拒否され（`WindowOpenRejectedError`）、`InventoryLink.moveTo()` は常に拒否されます（`InventoryLinkMoveRejectedError`）。配布用 JSON UI テンプレートと、クリック入力を実機イベントへつなぐ仕組みも未提供です。
> - **既定拒否は安全境界ではありません。** `WindowBuilder.setContainerAdapter()` は公開 API で、`canOpenScreens = true` を返し `openContainer()` を実装したテスト用アダプタを実機でも注入すれば画面は開きます。本番用アダプタの拒否は「うっかり開かない」ための既定値にすぎません。
> - **表示専用アイテムの保護はありません。** 画面を開くと表示アイテムは実際の `VirtualContainer` に `setItem()` で書き込まれ、入力抑制も JSON UI もないためプレイヤーが取り出せます。さらに `refresh()` や状態更新の再描画で同じアイテムが再設定されるため、**取り出しと再描画の組み合わせでアイテムが複製され得ます**。保護を実装するまで、この経路は安全ではありません。
> - そのため、環境確認と通常チェストの基準確認以外は、`open()` を明示的に許可するテスト用アダプタと、手動で用意した UI が揃うまで実施できません。チェックリストは「未実施」のまま残してください。
> - **実機での実験は使い捨てワールドだけで行ってください。** 本番ワールド・配布用ワールド・共有サーバーでは実行しないでください。
> - 現時点で自動で実施できるのは CLI と自動テストだけです。実機のクリック・アイテム保護・`InventoryLink` の安全性を、自動テストで代替しないでください。

## 1. 目的

次の未確定事項を、実際のゲームで確認します。

1. `VirtualContainer` のチェスト画面で、`button.send` などによる入力通知が成立するか。
2. JSON UI による通常操作の抑制と透明ボタンの重ね合わせが、PC・タッチ・コントローラーで機能するか。
3. InvUI の画面だけに JSON UI を適用し、通常のチェストへ影響させない判定ができるか。
4. `InventoryLink` のアイテム移動を有効化した場合に、重複・消失を防げるか（現行コアでは移動自体を拒否）。
5. 9 / 27 / 54 スロットと各入力方式で表示が整合するか。

これらは設計書の採用候補であり、**検証前の機能を「動作確認済み」として扱いません。** 個々の API の存在や挙動も、この手順の結果で確認する対象です。

## 2. 安全上の注意

- **使い捨てのテスト用ワールド**で実施する。本番ワールドや配布用ワールド、通常プレイヤーが入るサーバーでは行わない。試験後はワールドごと破棄してよい状態にする。
- 実施前にワールドと Resource Pack / Behavior Pack のバックアップを取る。
- 検証には価値のないアイテムだけを使う。`InventoryLink` の試験でも、回収不能になってもよいアイテムのみを使う。
- **表示専用アイテムは保護されていない。** 画面を開いたとき `setItem()` で置かれるだけで、プレイヤーは取り出せる。取り出した後に `refresh()` が走ると再設定され、複製が起こり得る。試験で表示アイテムを使う場合も、使い捨てアイテムだけにする。
- **テスト用アダプタは安全境界ではない。** `canOpenScreens = true` のアダプタを `setContainerAdapter()` で渡せば実機でも画面は開く。これは「テスト環境だから安全」という意味ではなく、使い捨てワールドでのみ行う理由そのものである。
- マルチプレイで試す場合は、参加者を限定したテスト用サーバーを使う。通常プレイヤーが入れる場所では有効化しない。
- JSON UI を手動で用意する場合は、既存の `ui/chest_screen.json` を直接書き換えず、バックアップと差分を保持する。CLI はこの作業を自動化しない。
- クリック・アイテム保護・JSON UI・`InventoryLink` は、この手順の合格が確認できるまで**安全に利用できない機能**として扱う。

### 即時中止する条件

次のいずれかが発生したら、その場で試験を中止し、アドオンと Resource Pack を無効化します。続行して「たまたま動いた」を合格にしません。

- 通常のチェスト（InvUI 以外）でアイテム移動が壊れた。
- 表示専用アイテムが持ち出せた、または操作で増減した。
- アイテムの複製・消失を確認した。
- 画面終了後やページ変更後に、古い通知がクリックとして実行された。
- チャット通知方式が通常チャットを壊した、または通知がプレイヤーに表示された。
- クライアントがクラッシュした、またはワールドが破損した。

## 4. 準備

1. テスト用ワールドを複製し、バックアップを取る。
2. 対象の Preview/Beta で Experimental API を有効にする。必要な設定はゲーム版によって異なるため、実際の画面で確認して記録する。
3. Behavior Pack を配置する。現行のコアは `Window.open()` を既定で拒否するため、実機試験には `canOpenScreens = true` を返すテスト専用アダプタを `setContainerAdapter()` で組み込んだテストビルドが必要。ただしこれは安全境界ではなく、使い捨てワールドでのみ実行する（本番用アダプタでは画面を開けないだけ）。
4. **JSON UI を入れる前に**、通常チェストの基準動作を確認する（手順 A）。
5. Resource Pack と JSON UI を入れる場合は、既存ファイルをバックアップし、手動でマージする。マージ内容とハッシュを記録する。
6. 検査だけなら、次の CLI を実行して静的状態を確認できる。

   ```bash
   node bin/cli.js init \
     --behavior-pack <Behavior Pack のパス> \
     --resource-pack <Resource Pack のパス> \
     --json
   ```

   CLI はパックを含めどのファイルにも書き込まず、検査結果を標準出力へ出すだけです。保存する場合は、利用者が標準出力をリダイレクトしてください。`--report` は廃止されており、指定すると引数エラーで失敗します。検査エラーがある場合は終了コード 1 になります。

7. 試験マトリクスを用意する。

| スロット数 | PC マウス | タッチ | コントローラー |
|---|---|---|---|
| 9 | 未実施 | 未実施 | 未実施 |
| 27 | 未実施 | 未実施 | 未実施 |
| 54 | 未実施 | 未実施 | 未実施 |

入力方式ごとに、対象画面のサイズ・UI スケール・言語設定も記録します。

## 5. 試験の順序

安全性の高い順に進めます。前の段階が不合格なら、後の段階へ進みません。

### A. 通常チェストの基準確認（JSON UI 導入前後）

通常のチェストを開き、チェスト間・プレイヤーインベントリ間でアイテムを移動する。JSON UI 導入後も、InvUI 以外のチェストで従来どおり移動できることを確認する。

- 対象 ID: `BASE-01` 〜 `BASE-03`
- 不合格の場合は中止。画面識別または入力抑制の設計を見直す。

### B. 表示の確認（9 / 27 / 54 スロット）

固定スロットのみの画面を開き、アイテムが正しい位置・個数・見た目で表示されるか、各スロット数・入力方式・画面サイズで確認する。現行コアは `Window.open()` を既定で拒否するため、この段階以降は `open()` を許可するテスト用アダプタを組み込んだビルドで実施する。**テスト用アダプタは安全境界ではない。使い捨てワールドでのみ実施する。**

- 対象 ID: `DISP-01` 〜 `DISP-03`
- あわせて、最終ページ・未使用スロットが空であることを確認する（ページ・タブ・スクロールを使うテストビルドが用意できた場合）。

### C. アイテム保護（表示専用・ボタン用スロット）

表示専用スロットのアイテムについて、通常クリック、Shift クリック相当、ドラッグ、ダブルクリック相当、ドロップ操作を試す。持ち出せないこと、個数が変わらないこと、複製・消失しないことを確認する。現行コアにはアイテム保護の実装がないため、保護を組み込んだテストビルドでのみ実施できる。

現行コアの画面は、表示アイテムを `setItem()` で置くだけで、入力抑制も JSON UI もない。プレイヤーは表示アイテムを取り出せ、その後に `refresh()`（状態更新・購読）が走ると同じアイテムが再設定されるため、**取り出しと再描画の組み合わせで複製が起こり得る**。この試験では、取り出し後に画面を操作して再描画させる手順も試す。

- 対象 ID: `PROT-01` 〜 `PROT-04`
- **1 つでも持ち出せたら不合格。** クリック通知の試験へ進まない。

### D. クリック通知

透明ボタン等の入力経路が利用できる場合に限り、通常クリックが Script API へ 1 回だけ届くか確認する。`button.send` → チャット通知は候補であり、採用確定ではありません。現行コアにはクリック入力を実機イベントへつなぐ仕組みも JSON UI もないため、この試験は入力ブリッジと UI を実装したテストビルドでのみ実施できる。チェスト画面で成立しない場合は不合格として記録し、別方式を検討する。

確認項目:

- 1 クリックにつき通知が 1 回か（`CLICK-01` 〜 `CLICK-03`）
- 通知からプレイヤーとスロットを特定できるか（`CLICK-04`）
- ページ変更・画面終了後の古い通知が破棄されるか（`CLICK-05`）
- 通知文字列が通常チャットとして表示されないか（`CLICK-06`）
- 同じ通知の連続送信で処理が重複しないか（`CLICK-07`）

### E. `InventoryLink` の安全試験

**必ず最後に、使い捨てアイテムだけで実施する。** リンクされたスロットと保管領域の間で、クリック・ドラッグ・カーソル上アイテム・画面終了・死亡を組み合わせ、増減が一致するか確認する。現行コアの `InventoryLink.moveTo()` は常に `InventoryLinkMoveRejectedError` を投げるため、移動を実装・明示的に有効化したテストビルドでのみ実施できる。それまでは「未実施」のまま残す。

- 対象 ID: `INV-01` 〜 `INV-05`
- 複製・消失が 1 件でもあれば中止し、`InventoryLink` を無効のままにする。

### F. ライフサイクルと再読み込み

死亡、ディメンション移動、切断、スクリプト再読み込みを試す。終了イベントの重複、古い入力の実行、`persistent` 状態の復元を確認する。画面の自動再オープンは標準保証としない。

- 対象 ID: `LIFE-01` 〜 `LIFE-05`

### G. 競合確認

他の Resource Pack と併用し、通常チェスト・InvUI 画面・UI の表示崩れを確認する。競合をゼロにできるとは保証しない。

- 対象 ID: `COMPAT-01`

## 6. 判定ルール

- 各項目は **合格 / 不合格 / 未実施 / N/A** で記録する。N/A は理由を必ず書く。
- 入力方式ごとに結果を分ける。PC で合格しても、タッチ・コントローラーの合格にはしない。
- 安全性に関わる項目（`BASE-*`、`PROT-*`、`INV-*`）が 1 つでも不合格なら、そのビルドは配布対象にしない。
- 全項目合格でも、**その試験で使った特定のゲーム版・`@minecraft/server` 版・入力環境**での合格にすぎない。ベータである事実は変わらない。
- クリック機能は、設計書 10.8 の合格条件を満たすまで正式機能として公開しない。
- `InventoryLink` は、アイテム安全試験を満たすまで制限付き・無効のままとする。

## 7. 記録と報告

- [CHECKLIST.md](CHECKLIST.md) をコピーし、試験ごとに記入する。
- 各項目に、再現手順、期待結果、実際の結果、スクリーンショットやログの有無を残す。
- 不合格時は、どの条件で再現したか（入力方式、スロット数、画面サイズ、操作順）を具体的に書く。
- CLI の検査結果（`--json`）を残す場合は、標準出力を利用者がリダイレクトして保管する。CLI 自身はファイルを書きません。ただし CLI は実機の入力・表示・アイテム安全を検証しない。
- ゲーム版や `@minecraft/server` 版が変わったら、同じ結果を流用せず再試験する。

## 8. 自動テスト（実機テストの代替ではない）

CLI の安全側の動作は、次のテストで確認できます。

```bash
node tests/manual-bedrock/cli.test.mjs
# または
node --test tests/manual-bedrock/cli.test.mjs
```

確認できること:

- CLI が Behavior Pack / Resource Pack を変更せず、どのファイルにも書き込まない。
- `--json` が単体でパースできる JSON を標準出力へ出し、`status` に `beta-unverified` を含める。
- 廃止した `--report` を指定すると引数エラーで失敗し、レポートファイルも作らない。
- 壊れた `manifest.json` で失敗し、パックを変更しない。
- 未検証・ベータであることを出力に含める。

確認できないこと:

- ゲーム内のクリック、アイテム保護、JSON UI の適用範囲。
- アイテムの複製・消失。
- 入力方式ごとの挙動。

## 9. 未確定のまま残す事項

以下は、この手順を実施して結果が出るまで確定しません。

- 入力通知方式（`button.send` → チャット通知を採用できるか）
- 表示専用スロットの操作抑制方法（現状は無保護で、取り出し＋再描画による複製が起こり得る）
- テスト用アダプタと本番用アダプタの実効的な差（`setContainerAdapter()` は公開 API のため、既定拒否は安全境界にならない）
- InvUI 画面だけに JSON UI を適用する識別方法
- `InventoryLink` の安全な移動手順
- 対応する Minecraft / `@minecraft/server` の版
- 9 / 27 / 54 スロットと画面サイズの整合性

結果が出るまで、README や CLI の出力に「動作確認済み」「安全」と記載しないでください。実機で試す場合は、結果にかかわらず使い捨てワールドだけで行ってください。
