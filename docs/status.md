# 実装状況と制約

実装の詳細と未検証事項をまとめています。ゲーム内の利用については、実機検証とコアの未完成点を確認してください。

Java版 [InvUI](https://github.com/NichtStudioCode/InvUI) の設計と公開 API をできるだけ維持した、Minecraft Bedrock Edition 向け GUI ライブラリです。

> [!WARNING]
> **ベータ / 実機未検証**
>
> - バージョンは `0.1.0-beta.1`。**npm には未公開**です。`npm install invui-bedrock` はまだ使えません。
> - **実機では一切検証していません。** ライブラリ経由の実機画面表示は**既定で有効**です。`minecraftVirtualContainerAdapter` は `canOpenScreens = true` を返し、`Window.open()` から `VirtualContainer` の作成・`VirtualContainer.open()`、`Window.close()` から `VirtualContainer.close()` を呼びます（すべて実機未検証）。実機ライフサイクルの後始末は、退出（`world.afterEvents.playerLeave`）と死亡（`world.afterEvents.entityDie`）が実装済みです（Node.js 上で確認済み、実機未検証。退出したプレイヤーの `opening` / `open` の Window を `PlayerLeft`、死亡したプレイヤーの Window も `PlayerDied` で close し、どちらも自動再オープンはしません。死亡は死亡した entity の id だけを照合するため、プレイヤー以外や他プレイヤーの死亡では close しません）。次元変更（`world.afterEvents.playerDimensionChange`）は `ServerClosed`、スペクテイターへの変更（`world.afterEvents.playerGameModeChange` の `toGameMode` が `Spectator`）は `PlayerSpectating` で close し、どちらもプレイヤーがまだ有効なのでアダプタにも close を要求します（Node.js 上で確認済み、実機未検証。他プレイヤーと Spectator 以外のゲームモード変更は無視）。shutdown は `system.beforeEvents.shutdown` で `opening` / `open` の全 Window を `ServerClosed` で close します（Node.js 上で確認済み、実機未検証）。このコールバックは restricted execution で走るため、`VirtualContainer.close()` とアダプタのイベント購読解除は呼ばず、画面とアダプタ購読の破棄はエンジンに任せ、チャット登録・state ハンドル・GUI/要素の購読などのローカル資源だけを解放します。close ハンドラー（およびそこで例外が起きた場合のエラーハンドラー）も同じ restricted なコールバック内で実行され、close ハンドラーは 1 回だけ呼ばれます。そこから `open()` しても画面は開かず `closed` のままです。shutdown 後の `open()` はモジュールの生存期間中ずっと抑止され、2 回目の shutdown は何もしません。スクリプト再読み込み時の後始末は未対応です。クリック入力はチャット通知の受信経路だけが既定で接続され、UI 側が通知を**自動生成**する処理はなく、通知は手入力で偽装でき、実機未検証です。JSON UI から押下 slot / session / layout-generation / sequence を自動生成して送る方式は、公式 `bedrock-samples` と Bedrock Wiki の範囲では根拠がなく実装していません。`InventoryLink` のアイテム移動は未実装です（itemChange の事後復元は実装済み・実機未検証）。JSON UI 連携は提供していません。`Item` の `display` / `button` 分類はメタデータとハンドラー実行のガードに留まり、実機のアイテム保護ではありません。`Window` は最初の `open()` で `world.beforeEvents.chatSend` を 1 本購読し、`!invui:<session-id>:<layout-generation>:<slot>:<sequence>` を解釈して `handleClick()` へ流しますが、これは Node.js 上で確認しただけで実機未検証です。`src/input.ts` と `src/chat-input-bridge.ts` は公開エントリから export していません。`WindowContainerAdapter` の任意購読フック（`subscribeClose` / `subscribeItemChange`）は既定の `minecraftVirtualContainerAdapter` も実装し、`world.afterEvents.virtualContainerClose` / `virtualContainerItemChange` を購読しますが、Node.js 上で経路を確認しただけで実機未検証です。既定のアダプタは公式 beta の購読オプション `{ containers: [container] }` で container ごとに購読を絞り、Window は届いた購読の container を対象として扱います。そのため `event.container` が `create()` の戻り値と同一参照でなくても close / itemChange を取りこぼしません（実機の同一参照は引き続き未検証）。どちらも `after` イベントなので、購読しても close・アイテム変更はすでに起きています。事前に防ぐことはできませんが、`Window` は itemChange でコンテナスロットを `beforeItemStack` へ戻し、次 tick > - **既定で実画面を開くため、アイテムの複製・消失リスクが既定で有効です。** 画面にはクリック通知を生成する UI がなく、アイテム保護は itemChange と entityItemDrop の事後復元だけで実機未検証です。表示アイテムは実際の `VirtualContainer` に `setItem()` で書き込まれ、プレイヤーが一瞬は取り出せます（その後、コンテナとプレイヤー側の変化を巻き戻す想定）。取り出した後に `refresh()`・状態更新・要素の更新通知で再描画が走ると、同じアイテムが書き戻されて複製され得ます。逆に、プレイヤーが入れたアイテムを再描画が上書きすると消失し得ます。試す場合は「[実機画面は既定で開く（使い捨てワールドで）](#実機画面は既定で開く使い捨てワールドで)」の条件だけに従ってください。
> - コア（レイアウト計算、アイテム表現、状態管理、Window の状態遷移）は実装・Node.js 上で確認済みです。**状態更新は解決後のレイアウトを比較し、要素が変わったスロットと状態に依存し得る Item だけを再評価（固定 `ItemStack` / `ItemBuilder` と `InventoryLink` はスキップ）、周期更新は Item を表示中の Window がある間のみ、永続ストアは手動の migration / レコード削除 API に加え、オプトインの `quarantineCorrupt` による破損レコードの自動退避・初期状態からの再開まで実装済みで、`migrations` に宣言した自動移行も `acquire()` が適用できます（未宣言の不一致は引き続き fail closed）**。クリック入力は、`window.ts` が最初の `open()` で `world.beforeEvents.chatSend` を購読し、`!invui:` 形式のチャット行を `system.run()` 経由で `handleClick()` に渡す経路だけが自動で接続されます（Node.js 上での確認のみ、実機未検証）。ただし UI 側がその通知を自動生成する実装はなく、同じ行はプレイヤーが手入力できるため、クリックの証明にはなりません。JSON UI から slot / session / layout-generation / sequence を自動生成する書式は公式構造から確認できていないため、JSON UI 連携は提供していません。
> - この README は、実装済みの範囲と未完成・未検証の機能を区別して記載します。未検証の機能を「完成・動作確認済み」として扱わないでください。

はモジュールの生存期間中ずっと抑止されます。shutdown 経路では close イベントは発生せず、2 回目の shutdown は何もしません。shutdown API がない環境では購読を諦めて Window は通常どおり動きます。スクリプト再読み込み時の後始末は未対応です。GUI の構造変更（種別・Structure 行・スクロール設定・タブ・`GuiLink` の子 GUI）で state schema が合わなくなった場合、`Window` はエラーハンドラーへ `WindowStateSchemaChangedError`（`INVUI_STATE_SCHEMA_CHANGED`）を報告し、再描画を停止して close します。同じ通知中に走った `setState()` は同じエラーで拒否され、以後の `setState()` は開いていない Window として失敗します。内容変更（`setContent`）は schema を変えないため、通常どおり描画だけ更新します。ページ・行・タブが新しいコンテンツ範囲外になった場合は、描画に使ったクランプ値を状態へ書き戻し（コンテンツ更新時と `setUpperGui()` 後、非表示だったタブを選択したとき）、コンテンツが再び増えても古い範囲外の値が復活しないようにします。`open()` は状態を書き戻さずクランプして描画するだけなので、小さいコンテンツ範囲を持つ Window を開いても、同じ共有状態を使う別 viewer のページ・行を巻き戻しません。`setUpperGui(gui)` は開いている Window の upper GUI を、Container と画面を維持したまま同じサイズ・同じ state schema ならその場で差し替えて再描画します。サイズが違う場合は再生成キューで新しい Container を生成して全スロットを描画してから旧画面を閉じて開き直し、その前に state を新しい schema へ再登録します（設計 8.4。page・line・tab・selection・data は新しい schema の初期値として引き継ぎます）。再登録は同じキーを別の Window が使用中、`session` の登録が残っている、`persistent` の登録がある場合に `SCHEMA_MISMATCH` で拒否され、現在の GUI・画面・state を維持したままエラーハンドラーへ報告します（保存レコードは書き換えません）。同じサイズで schema だけが違う場合は `WindowStateSchemaChangedError` を報告して close します（fail closed）。`setTitle(title)` は開いている Window のタイトルを、同じサイズの Container を新しく作って描画してから旧画面を閉じて開き直すことで変更します。state と購読は維持し、open/close ハンドラーは再実行しません。`open()` 実行中の変更は拒否し、旧画面を閉じた後に失敗した場合は Window を close します。close が実機で成功するかは未検証です。**画面を開く経路は既定で有効になりましたが、実機での表示・入力・アイテム保護は未検証です。**

## コアの実装範囲（実機非依存）

実機に依存しない範囲は実装され、Node.js 上で `@minecraft/server` をモックした状態で確認されています。Bedrock 実機での動作を保証するものではありません。

- **レイアウト**: `Structure`（最大 9×6、Unicode 1 コードポイント = 1 スロット）、`Gui.normal()` / `Gui.paged()` / `Gui.scroll()` / `Gui.tab()`、`PagedGui.itemsBuilder()`（Java版互換の別名）、`Markers.CONTENT_LIST_SLOT_HORIZONTAL` / `VERTICAL`、`GuiLink` による子 GUI の投影。ページ・行・タブは `GuiState` として外から渡し、GUI インスタンス自身は状態を持ちません。
- **アイテム**: `Item`、`ItemBuilder`、`Item.simple()`、`Item.builder()`、クリックハンドラーの登録と呼び出し順序、`Item.getMode()` / `setMode()` による `display` / `button` 分類（未指定はハンドラーの有無から推測、`setMode` はハンドラーを追加・削除しない）まで。`display` の Item はハンドラーを保持していても実行しません。ただし分類はメタデータと `Item` レベルのガードに留まり、JSON UI 側のアイテム保護（設計 7.2 / 10.1）ではありません。`updatePeriodically(ticks)` は、その Item を表示している開いた Window が 1 つ以上ある間だけ `system.runInterval()` に登録し、最後の Window が閉じるか購読を解除すると `clearRun()` で停止します。1 Item につき 1 インターバルで、再購読すると周期の位相はリセットされます。スケジューラの登録失敗は `console.error` に記録され、Item は明示更新では引き続き描画されます。クリックを実機イベントから届ける仕組みは、`world.beforeEvents.chatSend` を受ける自動接続だけが入っています（UI 側の通知生成は未実装・実機未検証。詳細は「コアの未完成点」の「入力」）。`Item.setPlaceholder(stack)` / `Item.builder().setPlaceholder(stack)` は非同期 provider の実行中に表示する `ItemStack` を設定します（clone して保持し、`undefined` で解除）。placeholder 未指定の非同期 provider は従来どおり解決まで待ち、指定時は途中で placeholder を表示して完了後に同じスロットを更新します。placeholder は表示だけの差し替えで、実機のアイテム保護ではありません。
- **インベントリ**: メモリ上の `VirtualInventory`（`Inventory` インターフェース実装）。`serialize()` / `VirtualInventory.deserialize()` は、呼び出し側が渡す明示的な `InventoryItemCodec` を介して JSON 可能なスナップショットへ変換・復元します（`ItemStack` の全状態は列挙できないため既定 codec は提供しません）。`serializeInventory(inventory, codec)` は同じスナップショットを任意の `Inventory`（読み取り専用の `PlayerInventory` を含む）から作れます。codec の `encode()` の戻り値とスナップショットは strict な JSON 検証と deep clone を通り、`serialize()` と `serializeInventory()` は最初の `encode()` より前に全占有 slot を clone して固定します。`deserialize()` は `item` が欠落した slot エントリを空 slot として扱わず拒否します。`InventoryLink` はリンク先スロットの読み書きと購読のみ提供し、**別インベントリへの移動は実装していません**。`PlayerInventory` はプレイヤーの実コンテナを同じ `Inventory` として読み取り専用で公開し、変更通知は呼び出し側が明示注入した `PlayerInventoryChangeSource` からのみ流れます（既定の自動接続はしない。`world.afterEvents.playerInventoryItemChange` を使う任意の `createPlayerInventoryChangeSource(signal, mapSlot)` もあるが、絶対スロットへの mapper は呼び出し側が実機で確認して渡す。詳細は「[プレイヤーインベントリ](implementation.md#プレイヤーインベントリ読み取り専用実機未検証)」）。
- **状態**: `StateManager`。`player` / `shared` のスコープ、`window` / `session` / `persistent` の保存期間、スキーマ不一致の拒否。永続化には `StateStore` が必要です。**`Window` の既定 `StateManager` は、ワールドが動的プロパティ API を持つ場合に `BedrockWorldStateStore` を自動で配線します（実機未検証）**。持たない環境や独自ストア・`onError` を使う場合は `WindowBuilder.setStateManager()` で注入します。**`StateManager.migrate()` による明示的な移行と、`migrations` に宣言した自動移行が実装済み**です。宣言のない旧 version/schema は自動変換せず拒否します。破損レコードは既定では自動退避・復旧せず、破損時は `StateCorruptionError` を投げてレコードを残します。`StateManager` の `quarantineCorrupt: true` を指定した場合だけ、`acquire()` が壊れた生値を退避して `initial` から再開します。削除は `StateManager.remove()` で明示的に行います。Bedrock 用には `BedrockWorldStateStore`（ワールドの動的プロパティを使用）を公開しています。
- **Window**: `Window.builder()` の設定、状態の取得・更新、`close()`、クリックのルーティング（`Window.handleClick()`）まで。開いた Window は自動でチャット通知の入力対象に登録され、close とページ/行/タブ変更で無効化されます（詳細は「[入力](#コアの未完成点実コードで確認)」）。状態が指名したレイアウトが描画完了して画面に書かれるまで、Container 再生成中、`placeholder` を指定しない非同期 provider が未解決の間は入力を拒否し、provider または `setItem()` が失敗したスロットは後で書き込みが成功するまで button として扱いません。`handleClick(slot)` は button mode の Item だけを実行し、キュー投入時と実行時の両方で slot・layout/generation・mode を再検証するため、close・再オープン・ページ/タブ変更をまたいだクリックは破棄されます。状態更新は解決後のレイアウトを比較し、要素が変わったスロット・状態に依存し得る Item・同じタイミングで通知されたスロットだけを再評価して描画します（固定 `ItemStack` / `ItemBuilder` と `InventoryLink` はスキップ）。GUI の内容変更と明示 `refresh()` は全スロットを再評価し、要素の更新通知は該当スロットだけを再描画します。同じサイズの `setUpperGui()` は要素が変わったスロットだけを描画します。状態更新と GUI 変更は 1 つの microtask（`Promise.then`。Bedrock の実行環境に `queueMicrotask` があるとは限らないため）にまとめ、同じタイミングで届いた要素の更新通知もスロット単位でその flush に合流させて 1 回だけ描画します。予約した時点でそのスロットの描画 token を進めるため、flush 前に解決した古い非同期結果は書き込まれません。**画面を開く経路は既定で有効（実機未検証）。** アダプタが任意フック `subscribeClose` / `subscribeItemChange` を実装していれば、`Window` は open 前に購読し、close イベントを close ハンドラーへ流し、itemChange はコンテナスロットを `beforeItemStack` へ復元したうえで、次 tick にプレイヤー側の所持品スロット／カーソルの変化を巻き戻します。復元の書き込みに失敗した場合だけ `WindowItemChangeDangerError` を報告して再描画を停止し、`close()` します。close ハンドラーの実行中に再 open すると新しい generation が始まり、それ以降の旧 generation の close ハンドラーは通知されず、再 open 後にそのハンドラーが投げた例外も新 generation には配送されません。既定の `minecraftVirtualContainerAdapter` も `world.afterEvents.virtualContainerClose` / `virtualContainerItemChange` は呼び出し側が渡す値のままです。どちらのイベントも `after` なので、購読した時点で close・アイテム変更はすでに起きています。itemChange は変更を事前に防ぐことはできませんが、コンテナスロットと、それに対応するプレイヤー側の変化を事後復元し、画面から直接地面へ捨てた場合は `entityItemDrop` の item entity ハンドルを解放する。プレイヤー以外や他プレイヤーの死亡は無視し、アダプタには close を要求しない）は実装済みですが、Node.js 上での確認のみで実機未検証です。次元変更時は同じ `open()` で購読した `world.afterEvents.playerDimensionChange` から `ServerClosed` で、スペクテイターへの変更時は `world.afterEvents.playerGameModeChange` の `toGameMode` が `Spectator` のときだけ `PlayerSpectating` で、viewer id が一致する Window を同じ close 経路で後始末します（プレイヤーがまだ有効なのでアダプタにも close を要求し、自動再オープンはしない。他プレイヤーと Spectator で走るため、`VirtualContainer.close()` とアダプタ/イベントの `unsubscribe()` は呼ばず、画面と購読の破棄はエンジンに任せ、chat 登録・state ハンドル・GUI/要素の購読・container 参照などのローカル資源だけを解放します。ユーザーの close ハンドラー（およびそこで例外が起きた場合のエラーハンドラー）も同じ restricted なコールバック内で実行され、close ハンドラーは 1 回だけ呼ばれるため、close ハンドラーから `VirtualContainer.close()` やイベント `unsubscribe()` を呼ぶと失敗し得ます。close ハンドラーから `open()` しても画面は開かず `closed` のままで、shutdown 後の `open()` はモジュールの生存期間中ずっと抑止されます。shutdown 経路では close イベントは発生せず、2 回目の shutdown は何もしません。shutdown API がない環境では購読を諦めて Window は通常どおり動きます。スクリプト再読み込み時の後始末は未対応です。GUI の構造変更（種別・Structure 行・スクロール設定・タブ・`GuiLink` の子 GUI）で state schema が合わなくなった場合、`Window` はエラーハンドラーへ `WindowStateSchemaChangedError`（`INVUI_STATE_SCHEMA_CHANGED`）を報告し、再描画を停止して close します。同じ通知中に走った `setState()` は同じエラーで拒否され、以後の `setState()` は開いていない Window として失敗します。内容変更（`setContent`）は schema を変えないため、通常どおり描画だけ更新します。ページ・行・タブが新しいコンテンツ範囲外になった場合は、描画に使ったクランプ値を状態へ書き戻し（コンテンツ更新時と `setUpperGui()` 後、非表示だったタブを選択したとき）、コンテンツが再び増えても古い範囲外の値が復活しないようにします。`open()` は状態を書き戻さずクランプして描画するだけなので、小さいコンテンツ範囲を持つ Window を開いても、同じ共有状態を使う別 viewer のページ・行を巻き戻しません。`setUpperGui(gui)` は開いている Window の upper GUI を、Container と画面を維持したまま同じサイズ・同じ state schema ならその場で差し替えて再描画します。サイズが違う場合は再生成キューで新しい Container を生成して全スロットを描画してから旧画面を閉じて開き直し、その前に state を新しい schema へ再登録します（設計 8.4。page・line・tab・selection・data は新しい schema の初期値として引き継ぎます）。再登録は同じキーを別の Window が使用中、`session` の登録が残っている、`persistent` の登録がある場合に `SCHEMA_MISMATCH` で拒否され、現在の GUI・画面・state を維持したままエラーハンドラーへ報告します（保存レコードは書き換えません）。同じサイズで schema だけが違う場合は `WindowStateSchemaChangedError` を報告して close します（fail closed）。`setTitle(title)` は開いている Window のタイトルを、同じサイズの Container を新しく作って描画してから旧画面を閉じて開き直すことで変更します。state と購読は維持し、open/close ハンドラーは再実行しません。`open()` 実行中の変更は拒否し、旧画面を閉じた後に失敗した場合は Window を close します。close が実機で成功するかは未検証です。**画面を開く経路は既定で有効になりましたが、実機での表示・入力・アイテム保護は未検証です。**

## コアの未完成点（実コードで確認）

「コア実装済み」は実機非依存の計算・状態遷移までを指します。次の項目は未完成、または実装済みでも制約・実機未検証が残ります。

- **実機画面**: 実アダプタは `canOpenScreens = true` を返し、`Window.open()` は Container を作成して `VirtualContainer.open()` を呼びます。`close()` は `VirtualContainer.close()` を呼びます。ただし**実機で画面が表示されるか、close がいつ完了するかは未検証**です。`close()` は閉鎖を要求した時点で返り、実際の close イベントは別 tick になることがあるため、直後の再 `open()` は前画面の閉鎖待ちで失敗し得ます。この場合の `PreviousScreenClosing` だけは、`Window.open()` と内部再生成が後続 tick で最大 20 回再試行します（他の open エラーはそのまま失敗します）。表示されたアイテムの取り出しを事前に防ぐ仕組みはなく、itemChange の事後復元（実機未検証）に依存します。
- **実機ライフサイクル**: 既定の `minecraftVirtualContainerAdapter` は `world.afterEvents.virtualContainerClose` / `virtualContainerItemChange` を購読し、`Window`（open 前に購読し、close または失敗した open で解除）が close ハンドラーと itemChange の危険通知に流します。ただし Node.js 上で確認しただけで実機未検証であり、どちらも `after` イベントなので close・アイテム変更を事前に防ぐ保護ではありません。itemChange はコンテナスロットと、対応するプレイヤー側の所持品／カーソル変化を事後復元します（実機未検証）。`world.afterEvents.playerLeave` は最初の `open()` で 1 本購読し、退出したプレイヤーの Window を `PlayerLeft` で close して後始末します。同じ `open()` で `world.afterEvents.entityDie` も 1 本購読し、死亡した entity の id が viewer id と一致する Window（`opening` / `open`）だけを `PlayerDied` で close して同じ経路で後始末します（プレイヤー以外・他プレイヤーの死亡、id を読めない entity は無視。アダプタには close を要求しません）。どちらも Node.js 上で確認しただけで実機未検証です。`entityDie` の検出は `playerLeave` とは別に行い、片方が無い環境でも他方は動きます。`world.afterEvents.playerDimensionChange` と `world.afterEvents.playerGameModeChange` も同じ `open()` で 1 本ずつ購読し（feature detection も別々）、次元変更は `ServerClosed`、`toGameMode` が `Spectator` のときだけ `PlayerSpectating` で close します。こちらはプレイヤーがまだ有効なのでアダプタにも close を要求します（Node.js 上で確認済み、実機未検証。他プレイヤーと Spectator 以外のゲームモード変更は無視。自動再オープンはしない）。`system.beforeEvents.shutdown` も同じ最初の `open()` で 1 本購読し、shutdown 時は `opening` / `open` の全 Window を `ServerClosed` で close します（Node.js 上で確認済み、実機未検証）。ただし shutdown のコールバックは restricted execution で走るため、`VirtualContainer.close()` とアダプタ/イベントの `unsubscribe()` は呼びません。画面と購読の破棄はエンジンに任せ、chat 登録・state ハンドル・GUI/要素の購読・container 参照などのローカル資源だけを解放します。close ハンドラーも同じ restricted なコールバック内で 1 回だけ実行され、そこで `open()` しても画面は開かず `closed` のままです。shutdown 後の `open()` はモジュールの生存期間中ずっと抑止され、2 回目の shutdown は何もしません。shutdown API がない環境では購読を諦め、Window は通常どおり動きます。スクリプト再読み込み時の後始末は実装していません。`Window` の `status` 遷移、状態ハンドルの解放、`close()` の明示呼び出しはありますが、これらは実機の画面終了を保証しません。
- **入力**: `Window.handleClick(slot)` は呼び出し側が論理スロットを直接渡す API です。button mode の Item だけを実行し、キュー投入時と実行時の両方で slot・layout/generation・mode を再検証するため、待機中に close・再オープン・ページ変更があったクリックや、display に変わったスロットのクリックはハンドラーを呼ばずに破棄されます。左右・Shift・ダブルクリックの区別はありません。

  **入力は、描画が完了して画面に書かれたレイアウトにだけ向きます。** 状態変更で `_inputLayoutGeneration` が進んでも、その世代のレイアウトを render が適用して全スロットを描き終えるまでは入力ゲートが closed で、チャット通知は button が無いものとして拒否され、`handleClick()` も `false` を返します（ハンドラーは実行しません）。同じゲートは、Container 再生成（`setTitle()` / サイズ変更 / サイズ違いの `setUpperGui()`）が swap してから新しい画面を開くまでの間も closed です。`placeholder` を指定しない非同期 provider が未解決の間は closed が続き（解決しない限り開かない。タイムアウトはない）、provider または `setItem()` が失敗したスロットは、後でそのスロットへの書き込みが成功するまで `display` 扱いで button になりません。close・再オープンはゲートをリセットし、新しい open の描画完了後に開きます。これらはいずれも Node.js 上での確認のみで実機未検証です。
  既定では、`Window` が最初の `open()` で `world.beforeEvents.chatSend` を 1 本購読し、`!invui:<session-id>:<layout-generation>:<slot-index>:<sequence>` 形式の行を `system.run()` 経由で `handleClick()` へ流します（[src/chat-input-bridge.ts](../src/chat-input-bridge.ts)、Node.js 上で確認済み）。session-id は open ごとに作り直される `Window._inputSessionId`（`Window.id` の `window-N` ではありません。`window-N` は再読み込みで再利用されるため、遅延した通知が新しい画面に一致し得ます）で、送信者 id と一致する開いている Window だけが対象です。`_inputSessionId` は公開クラス `Window` の公開 getter（`dist/window.d.ts`）で、値は `session-<36進の時刻>-<36進の連番>-<36進6文字>` 形式の不透明なトークンです。`_inputLayoutGeneration` も公開 getter で、open ごとに `0` から始まり、ページ/行/タブまたはスロット要素の変更で進みます。通知の `layout-generation` はこの値と照合されるため、ページ変更前に生成され変更後に届いた行は、新しいページの同じスロットが button でも `stale-layout-generation` として拒否されます。世代を持たない旧3フィールド形式 `!invui:<session>:<slot>:<sequence>` は受理しません。どちらもアンダースコア付きで内部扱い・互換保証なしですが、開発者が現在値を読むことはできます。解析・重複排除・直列 queue は [src/input.ts](../src/input.ts) の `createInputAcceptor()` が担い、close とページ/行/タブ変更でキュー世代を進めて待機中の通知を捨て、実行時に通知の `layout-generation` も再照合します。スロットは現在のレイアウトの mode で再評価され、button 以外（display・inventory）は拒否されます。解析に成功した行は `cancel` で通常チャットから隠します（偽装行も隠れます）。
  ただし、**この経路はクリックの証明でも認証でもありません。** 行はプレイヤーが手入力でき、sender id 以外の全フィールドが攻撃者制御です。rate limit は既定で 100 ms（`minIntervalMs: 100`、10 回/秒）有効で、直前の受理から 100 ms 以内に送った通知は `rate-limited` として拒否します（`open()` をまたいでも直前の受理時刻を引き継ぎます）。時刻ベースの有効期限は別途ありません。この間隔は `Window` の自動接続では内部既定値で、パック側から変更する API はありません。UI 側が通知を生成する実装（`button.send` ペイロード）はリポジトリにありません。実機での `button.send` と表示アイテムの扱いは未検証で、アイテム保護・入力抑制はこの経路に含まれません。`src/input.ts` と `src/chat-input-bridge.ts` は `src/index.ts` から export していません。`world.beforeEvents.chatSend` か `system.run` がない環境では接続せず、chat 入力は fail closed になります。チャット送信からの入力経路は、実機で `button.send` の挙動を確認するまで正式機能にしません。
- **差分描画**: 状態更新では、前回描画したレイアウトと解決後のレイアウトを比較し、要素が変わったスロットと直前の書き込みに失敗したスロットだけを再評価します。要素が同じスロットも、provider が Window の state を読めるか証明できない限り再評価します。固定 `ItemStack` / `ItemBuilder` の Item は Window も state も受け取らず、`InventoryLink` はインベントリ側の通知で更新されるため、状態更新ではスキップできます。Bedrock の `ItemStack` を全 component まで比較して同値判定はしません。GUI の内容変更と明示 `refresh()` は、要素参照が変わっていなくても全スロットの provider を再評価します（明示 `refresh()` は外部の可変データも読み直す経路のため）。同じサイズ・同じ state schema の `setUpperGui()` は、Window の状態が変わらないので要素が変わったスロットと直前の書き込みに失敗したスロットだけを再評価して描画します（クランプが必要なら全スロット描画に回ります）。どの描画でも **`setItem()` を省略するのは、その Container に対して直前に自分で空を書いたスロットを空で上書きする場合だけ**です（空→空のみ、表示アイテムの書き込みはスキップしません）。要素の更新通知だけが該当スロットを再描画しますが、状態更新・GUI 変更・同じタイミングの複数の要素の更新通知は 1 つの microtask に合流して 1 回だけ描画します。詳細と限界は「[差分描画の限界](implementation.md#差分描画の限界状態更新)」を参照してください。レイアウトサイズが変わった場合、表示中の Window は再オープンが必要で、`refresh()` はエラーを報告するだけです。
- **周期更新**: `Item.updatePeriodically()` は実装済みですが、実機未検証です。Bedrock の `system.runInterval()` に接続するのは、その Item を表示している開いた Window がある間だけで、Window を開く前や最後の Window を閉じた後は実行されません。1 Item につき 1 インターバルで、購読の張り替えで周期の位相がリセットされます。スケジューラの登録に失敗した場合は `console.error` に記録され、自動の再試行はありません。
- **永続ストア**: `StateManager` は注入された同期 `StateStore` に JSON を読み書きします。`STATE_STORAGE_VERSION` と schema の不一致は `StateConflictError`、壊れた JSON や不正な `guiState` は `StateCorruptionError` で失敗し、レコードは変更しません。**`StateManager.migrate()` による明示的な移行と、`migrations` に宣言した自動移行が実装済み**です。宣言のない旧 version/schema は自動変換せず拒否します。破損レコードの自動退避・復旧は既定では行いません。`StateManager` の `quarantineCorrupt: true` を指定したときだけ、`acquire()` が壊れた生値を `...:quarantine` キーへ退避して元キーを削除し、`onError` で通知して `initial` から再開します（`migrate()` は対象外）。明示的な削除は `StateManager.remove()` です。永続状態の `set()` が `setItem()` を実行している間はその identity をロックし、ストア実装から同じ identity の `acquire()` / `set()` / `migrate()` / `remove()` を再入すると `LIVE_STATE` の `StateConflictError` で拒否します（再入した書き込みが後から黙って上書きされるのを防ぐため。他の identity は影響を受けません）。ストアの保存失敗は `onError`（未指定ならログ）へ通知してから同じエラーを投げ、状態はコミットしません。直前の正常なレコードが残るので再試行・再読み込みでの復元が可能です。`Window` 経由（`open()`・クリック・再描画）の失敗は Window のエラーハンドラーにも届きます。外部 `StateStore` の `setItem()` が途中で失敗して部分的な書き込みが残っても、`StateManager` はそれを検出・修復しません（ストア実装の原子性に依存します）。Window の schema は GUI 種別・Structure 行・スクロール設定・タブと `GuiLink` の子 GUI を再帰的に含む識別子で、循環参照は拒否されます。

### 実機画面は既定で開く（使い捨てワールドで）

- **既定の実アダプタが実画面を開きます。** `minecraftVirtualContainerAdapter` は `canOpenScreens = true` を返し、`Window.open()` は `world.virtualContainerManager.create()` で `VirtualContainer` を作成して `VirtualContainer.open()` を呼び、`Window.close()` は `VirtualContainer.close()` を呼びます。**実機で表示・close が成立するかは未検証**です。`close()` は要求時点で返り、実際の close イベントは別 tick になることがあるため、閉鎖直後の再 `open()` は失敗し得ます。
- **クリック通知は UI 側が生成しません。** `Window` は `world.beforeEvents.chatSend` を購読し、`!invui:` 行を `handleClick()` へ流す受け口だけを持ちます（Node.js 上で確認済み・実機未検証）。通知はプレイヤーが手入力でき、送信者 id 以外は偽装可能です。`Item` の `button` 分類はハンドラー実行ガードにすぎません。クリックの取りこぼし・遅延入力・意図しないスロットへの適用を保証できません。
- **アイテム保護は事後復元のみで、実機未検証です。消失・複製事故の恐れが残ります。** 表示専用・ボタン用スロットのアイテムは、プレイヤーが画面から取り出すと `virtualContainerItemChange` でスロットが `beforeItemStack` へ戻され、次 tick の照合でプレイヤー側の所持品スロット／カーソルからも取り除かれます。プレイヤーが元から持っていたアイテムは書き換えません。ただし `after` イベントによる事後復元なので、対応するプレイヤー側イベントや item entity を特定できない移動、複数プレイヤー・複数 Window が同じアイテム種を同時に動かす場面は保証されません。このリスクは既定で有効です。
- **itemChange は事後復元で、事前抑止ではありません。** 既定の `minecraftVirtualContainerAdapter` は `subscribeItemChange` を実装して `world.afterEvents.virtualContainerItemChange` を購読しますが、これは Node.js 上で経路を確認しただけで実機未検証です。`after` イベントなので変更はすでに起きており、`Window` はスロットを `beforeItemStack` へ戻し、次 tick にプレイヤー側の所持品スロット／カーソルを巻き戻します。画面から直接地面へ捨てた場合は `entityItemDrop` で記録した item entity を削除します。復元に失敗した場合だけ `WindowItemChangeDangerError` を報告し、再描画を停止して `close()` を要求します。この復元が実機で成立するか、取り出しが一瞬でも可能かは未検証です。

コアの型・レイアウト計算・状態管理は Resource Pack なしで利用できます（Node.js 上で `@minecraft/server` をモックした状態で確認済み）。既定の実アダプタは `Window.open()` で実画面を開こうとしますが、実機未検証であり、クリック入力と itemChange の事後復元が実機で成立するかは確認していません。

## 設計上の前提（実機未検証）

以下は設計書の方針です。実機で確認されるまで動作保証として読み替えないでください。

- `VirtualContainer` は Bedrock Preview/Beta の Experimental API で、メモリ上のコンテナであり、ワールドに保存されない。
- `size` と `title` は生成後に変更できないため、変更時は画面を開き直す。
- ワールド終了時は `system.beforeEvents.shutdown` で `opening` / `open` の Window を `ServerClosed` で close する（restricted execution のため `VirtualContainer.close()` とアダプタのイベント購読解除は呼ばず、画面・アダプタ購読の破棄はエンジン任せ）。スクリプト再読み込みは未対応で、この後始末は走らず、close ハンドラー・状態解放・永続化は保証されない。通常の終了イベントに依存した永続化はできない。
- プレイヤーの次元変更は `ServerClosed`、スペクテイターへの変更は `PlayerSpectating` で Window を close する（設計 13.1）。どちらも viewer id が一致する Window だけが対象で、自動再オープンはしない。
- 状態の共有範囲は `player` / `shared`、保存期間は `window` / `session` / `persistent`。
- 設計原則は影響を受けたスロットの差分反映で、**状態更新はレイアウト差分で変更スロットと状態に依存し得る Item だけを再評価する**（要素の更新通知は該当スロット。GUI の内容変更と明示 `refresh()` は全スロット再評価）。状態更新・GUI 変更は 1 つの microtask にまとめて 1 回だけ描画し、同じタイミングの要素の更新通知はスロット単位でその flush に合流させる。理由と限界は「[差分描画の限界](implementation.md#差分描画の限界状態更新)」を参照。
- JSON UI の変更は必要最低限とし、通常チェストへの影響を避ける。
- **Mojang は `data_driven_container_screen.json` と `data_driven_container` 名前空間を変更しないことを期待し、後方互換性を保証していません**（Minecraft Preview 26.70.23 告知）。このため、この JSON / 名前空間の変更や、それに依存する入力・画面接続を前提にしません。`VirtualContainer` がこの画面を使うか自体も未確認です。
- `@bedrock-core/ui` には依存しない。
